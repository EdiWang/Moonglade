## Confirmed requirements

- Moonglade has one local owner account, established during setup. The local email/password form remains available. Local setup, local sign-in, and local TOTP policy retain their current behavior. Each site can configure one standards-based OIDC provider and bind one external account. Microsoft Entra ID with a specified tenant is the live acceptance provider. Provider names, authority URLs, and vendor-specific behavior do not belong in application code or UI resources.
- Account Settings manages the owner-supplied display name, OIDC authority, client ID, client secret, and identity binding. A saved configuration takes effect without a process restart. Match later callbacks against the configured provider and the validated issuer and subject. External profile claims never change the local owner or public profile.
- Support public HTTPS authorities and provider endpoints. The server's OIDC backchannel only connects to public addresses.
- Show one SSO sign-in button only when the configuration is enabled and a binding is ready for sign-in. Use the owner-supplied provider name in the button. A matching OIDC callback signs in as the same local owner without Moonglade TOTP, even if local password sign-in requires it.
- An SSO session can use Account Settings. Changing the local password, login email, or authenticator requires the current local password. Configuration changes, binding, and unbinding require the current local password and a code from an enrolled Moonglade authenticator. When TOTP is required and enrollment has been reset, finish re-enrollment before managing SSO. When TOTP is optional and no authenticator is enrolled, the current password suffices.
- Adding third-party sign-in uses a wizard. Enter provider settings first, verify the local password and applicable TOTP on a dedicated page, then bind and confirm the external account. A later binding without reusable proof also opens the dedicated verification page.
- When the owner saves the provider configuration and immediately starts binding in the same short-lived flow, reuse the password and applicable TOTP proof. A separate binding attempt started later requires fresh proof. After a valid OIDC callback, show the external account in Account Settings and save the binding only after the owner explicitly confirms it. Cancellation or failure leaves the configuration saved and the account unbound.
- Allow rotating the client secret in place and require unbinding before changing the authority or client ID. Unbinding removes the sign-in option and immediately revokes sessions issued through that binding. Sign-out only ends the Moonglade session.
- Disabling keeps the configuration and binding, hides the sign-in button, rejects pending SSO sign-ins, and immediately revokes SSO sessions. Re-enabling permits fresh sign-ins through the saved binding. Revoked sessions stay revoked. Deleting requires confirmation, clears the configuration, client secret, and binding, and revokes SSO sessions. Disabling and deleting preserve local sessions.
- Old OIDC configuration and sessions may be retired without migration. For an existing OIDC-only installation, restrict access before starting the upgraded site, then use the existing public setup page to establish local credentials. Preserve the owner profile, prefill its existing public email where available, and keep unrelated data. An existing initialized local account keeps its credentials and skips setup.
- Retire the legacy `/auth/identity` endpoint with the old allowlist. The route returns 404.
- A database backup and restore must recover the saved OIDC configuration, binding, and ability to decrypt the client secret on a replacement Docker instance. The existing database stores both the encrypted client secret and the usable Data Protection key ring. No separate key volume, certificate, master secret, or cloud service is required. A database backup contains enough material to decrypt the client secret, so handle it as credential-bearing material. Keep the client secret out of settings responses, rendered fields, logs, activity details, diagnostics, and this record.

## Current code and project constraints

- [Auth registration](../src/Moonglade.Auth/ServiceCollectionExtensions.cs) uses the application cookie and administrator role. [Cookie validation](../src/Moonglade.Auth/LocalAccountCookieEvents.cs) checks the owner ID and account revision, then validates local TOTP eligibility or the OIDC binding revision. The [OIDC handler](../src/Moonglade.Auth/Oidc/OwnerOidcHandler.cs) uses request-scoped configuration for binding and sign-in. Binding issues a pending ticket, and sign-in issues a local owner cookie after matching the active binding.
- [Setup gate](../src/Moonglade.Web/Services/LocalAccountSetupGateMiddleware.cs) applies to all installations. [SetupAccount](../src/Moonglade.Web/Pages/SetupAccount.cshtml.cs) prefills an existing profile email and commits local credentials on the same owner row. Preserve public setup, health and static exceptions, the retired identity route's 404, and the API/feed 503 behavior.
- [Sign-in](../src/Moonglade.Web/Pages/SignIn.cshtml.cs), [sign-out](../src/Moonglade.Web/Controllers/AuthController.cs), [account operations](../src/Moonglade.Web/Controllers/AccountController.cs), and [Account Settings](../src/Moonglade.Web/Pages/Admin/LocalAccount.cshtml) use the local owner foundation. Reuse the existing Account Settings rows and dialogs, rate limiting, and localization patterns.
- Keep Auth responsible for authentication and credential storage, Web responsible for routes and UI, and EF mappings and initialization in their existing projects. PostgreSQL uses snake_case and SQL Server uses PascalCase. Any schema change requires manual, idempotent scripts for both providers. Preserve normal fresh creation and seeding. Check startup emptiness detection and full-database maintenance paths if adding a mapped table. Follow [repository rules](../AGENTS.md), the applicable [engineering reference sections](agent-reference.md), [database rules](../database/README.md), and the [test guide](../src/Tests/README.md). The Java toolchain is excluded by the user's repository instructions.
