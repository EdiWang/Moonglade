## Configuration And Environment

Host configuration uses `src/Moonglade.Web/appsettings.json`, local Development overrides, and standard environment variables (`:` becomes `__`). See [README](../README.md) for configuration examples. Keep local overrides secret-safe as required by AGENTS.md.

Additional keys and implementation constraints:

| Key or section | Purpose | Required? | Notes |
| --- | --- | --- | --- |
| `ConnectionStrings:MoongladeDatabase` | Database connection string. | Yes | Do not document or commit production values. |
| `ConnectionStrings:DatabaseProvider` | Selects `PostgreSql` (default) or `SqlServer`. | Yes | Keep provider names aligned with `AddMoongladeDatabase`. |

| `Authentication:LocalAccountRateLimit` | Fixed-window rate limiting for local password sign-in and TOTP verification attempts. | Optional | Defaults to enabled, 10 attempts per 1 minute, partitioned by client IP and account context. |
| `CommentRateLimit` | Built-in comment submission rate limiting by client IP and post ID. | Optional | Uses a fixed window policy. |

SMTP delivery uses `Edi.TemplateEmail.Smtp` with explicit `FromAddress` and `SenderAddress` set to the effective SMTP sender address. Map `Email:EnableSsl` and the port to `SmtpSettings.SocketOptions`: port 465 uses `SslOnConnect`; other ports use `StartTls` when enabled and `Auto` otherwise. The test email template displays this effective security mode.

`Edi.TemplateEmail` and `Edi.TemplateEmail.Smtp` use version `2026.8.0`. The singleton `IEmailHelper` validates and holds template configuration; each `ForType` call returns an independent `IEmailBuilder` that owns the mappings and builds one message. Keep builders local to each notification and mock `IEmailBuilder` separately from `IEmailHelper` in tests.

HTML email bodies encode ordinary mapped values. Only wrap the already-rendered new-comment body and administrator reply HTML in `TrustedHtml` to preserve the output of `ContentProcessor.MarkdownToCommentHtml`. Keep original comment text, names, titles, and URLs as ordinary mappings; do not pre-encode them. `TrustedHtml` does not sanitize its input.

## Main Business Logic

### Blog Content

- Posts are the core entity, defined by `Moonglade.Data.Entities.PostEntity`. Their lifecycle is represented by `PostStatus`, including draft, published, and scheduled states.
- Post creation and updates are handled by commands such as `Moonglade.Features.Post.CreatePostCommand` and `UpdatePostCommand`. The Web-layer save workflow lives in `Moonglade.Web/Commands/PostManagementCommands.cs` and coordinates create/update, activity logs, scheduled publishing wake-up, Webmention, and IndexNow. Cache invalidation is triggered by feature-level `PostChangedEvent` publication after database commit.
- Recycle, publish, and unpublish endpoints dispatch their feature commands directly from `PostController`, then use the inherited `LogActivityAsync` method. Keep the save workflow for its scheduling and notification coordination; do not add forwarding workflow commands for simple state operations.
- Published posts generate a `RouteLink` based on publish date and slug. Do not casually change the published URL shape because old links, RSS/Atom, sitemap, search engines, and caches depend on it.
- Article state writes use `PostEntityHelper.SetStatus` to assign `PostStatus`, `PubDateUtc`, `ScheduledPublishTimeUtc`, and `RouteLink` together. Only draft, scheduled, and published are valid write states; deletion remains an independent `IsDeleted` flag. Published writes clear scheduled time; draft and scheduled writes clear publication time and route. Callers choose timestamps: editing a published post preserves its publication date, manual publishing uses the current time, and scheduled publishing uses its actual execution time without changing `LastModifiedUtc`. Resolve creation slug conflicts and apply edited slugs before generating the route.
- Scheduled publishing converts client local time to UTC and is handled by `ScheduledPublishWakeUp` / `ScheduledPublishService`. The next-time query includes overdue schedules and ignores deleted posts or missing schedule times, so enabling the worker dispatches already-due work without a five-minute polling delay. Persisted and cross-boundary timestamps should use UTC.
- `PublishScheduledPostCommand` retains its affected-entry count and existing cutoff/execution-time samples. After a successful nonempty save, it captures a read-only `ScheduledPostsPublishedEvent` list containing only post ID, title, and actual publication UTC time. Attempt `PostChangedEvent` first, then the independent publication handoff even if cache notification throws; log an isolated handoff failure without masking the original cache exception. The Web event handler writes one best-effort `post.automatically-published` System activity per captured post, without request/account context, and continues after individual failures. `CreateActivityLogCommand.EventTimeUtc` optionally supplies an occurrence timestamp under the shared UTC validation contract; omitted values retain current UTC write time. This is in-process notification, not durable delivery or cross-host deduplication; published statuses prevent a later normal scheduler pass from repeating entries.
- Pages, categories, tags, assets, recycle bin behavior, and related blog features live under the relevant feature folders in `Moonglade.Features`.

### Comments And Moderation

- The public comment entry point is `Moonglade.Web.Controllers.CommentController`; comment creation is handled by `Moonglade.Features.Comment.CreateCommentCommand`.
- Whether comments are enabled, require review, close after a number of days, or use word filtering comes from `IBlogConfig.CommentSettings`.
- `CommentSettings.EnableMarkdownLinks` controls comment/reply rendering across public/admin views and newly generated email. Preserve the [documented behavior](../README.md#comment-markdown-links), including default-off links and protocol/rel validation.
- Built-in comment creation is also protected by host-level `CommentRateLimit` settings that partition requests by client IP and post ID.
- Built-in comment creation checks `CommentSubmissionGuard` honeypot and elapsed-time fields before dispatching the create command.
- Content moderation is abstracted in `Moonglade.Moderation` and supports local keyword filtering. Do not put moderation behavior directly in controllers.
- Administrator comment moderation and replies produce activity logs; public comment submissions do not. Comments, replies, and Webmentions can trigger email notifications. Email notification handlers should enqueue to the database outbox; external delivery belongs in `EmailOutboxWorker` instead of request handlers.

### Configuration

- Ordinary runtime preferences are managed by `Moonglade.Configuration.BlogConfig` and persisted in the `BlogConfiguration` table. When adding an ordinary group, follow `IBlogSettings<T>`, provide `DefaultValue`, and add its property to `BlogSettingsSnapshot` and its typed load to `BlogConfig.Parse`. This pure parser is the single ordinary-default list: it returns a snapshot and the exact default JSON for `ConfigInitializer` to persist, without changing runtime state. The ten-group ordinary reader excludes credentials, public owner email and installation history. Auth owns `OwnerAccountStore` and the independent account table; Setup owns `SystemManifestSettings`. The obsolete `LocalAccountSettings` JSON is never parsed, seeded or written at runtime; the manual account cutover deletes it.
- The ten ordinary groups and nested menu values are sealed, non-positional init-only records; menus/submenus use `ImmutableList`, retaining disabled null menus and legacy JSON arrays. Reuse the current types for HTTP inputs; keep the existing mutable menu JSON envelope. Do not add a parallel DTO/model hierarchy without a demonstrated binding incompatibility. Use `with` to prepare replacements rather than JSON round-trip copying or property mutation.
- Pronouns are no longer a setting or profile display feature. Legacy `pronouns` JSON is ignored during parsing and is not rewritten at startup; the next ordinary General save omits it. Do not retain an inactive model property or add automatic data cleanup for this removed feature.
- `IBlogConfig` is a read-only consumer boundary with `Capture()`; loading and publication belong to the concrete singleton `BlogConfig`. Register that owner and alias the reader to the same instance. A capture retains one immutable ten-group root. Publication exchanges its reference once; old roots/children remain valid. The reader and concrete owner expose no per-group forwarding properties: capture once at the start of a logical operation, before awaits, and pass the captured root or its relevant immutable group through related calls. Comment/reply domain commands, email events, and feed queries can carry a JSON-ignored snapshot for their initiating operation; independent calls capture fresh state. Keep these in-process contexts out of HTTP and durable email payloads.
- Razor handlers and views use `ViewData.CaptureSettings(SettingsReader)`. The global `BlogSettingsFilter` seeds native Page/PageModel ViewData before page handlers and View/Partial result data before rendering, preserving an existing handler capture. Layouts, partials, and menu/tag components reuse that ViewData entry, including copied child dictionaries. Explicitly seed standalone render data before preparing related state. Do not cache settings in HttpContext.Items or a request-scoped frozen reader: a separate operation or new render can capture newly published state in the same HTTP context.
- Ordinary persisted JSON uses `DefaultValue` for completely absent fields as well as missing groups. `FromJsonWithDefaults` adds only absent top-level properties in memory, using the existing serializer's case-insensitive names and preserving the order of duplicate saved properties. Explicit false/zero/null/empty arrays remain saved values, not missing fields. Valid partial JSON and its timestamp are not rewritten. Keep this behavior at the persisted-loading boundary rather than changing request-model constructors or the shared `FromJson` behavior. Account and manifest parsing is excluded so missing credential/history fields cannot acquire bootstrap defaults.
- The loader and update handler use DataAnnotations and model-owned `IValidatableObject` rules without mutating inputs. Validate every replacement before querying/changing settings rows. `SettingsValidationAttribute` translates command validation failures on settings endpoints to HTTP validation problems; HTTP model validation alone does not protect parsed menu graphs or non-HTTP callers. Keep nested menu validation in its settings model and script/CSS conditions out of controller-only checks.
- Startup restores malformed, incompatible, null, or semantically invalid ordinary settings to whole-group defaults in their existing rows, including otherwise valid sibling fields; valid settings and timestamps are preserved. Explicit saved values are retained only when valid. `AddDefaultConfigurationCommand` serves this startup initialization/repair path only. Invalid persisted `SystemManifestSettings` must stop initialization before repair writes with an actionable key-only error, preserving installation history. Never create default credentials or log stored JSON.
- Preserve approved validation compatibility: blank notification names retain deployment fallback; unknown theme IDs retain fallback; feed count allows 0 through `int.MaxValue`; CSS is capped at 10240 UTF-8 bytes; disabled menu arrays may be null. Existing watermark font/text rules apply even when disabled. Independent account writes validate email and new-password syntax, preserve credential-state constraints and use Otp.NET for authenticator proof. Manifests require a non-minimum UTC time while preserving arbitrary/empty version strings.
- First-install seeding requires all mapped application tables to be empty, not only `BlogConfiguration`. Maintain the emptiness checks and their coverage when adding application tables. An existing empty schema may be initialized. Seed data and default settings share one provider execution-strategy transaction; retries clear tracked inserts and verify a potentially committed installation before reseeding. Never clear existing or ambiguous older partial-install data. Schema creation and noncritical site-icon generation are outside this data transaction.
- `ConfigInitializer.InitializeStoreAsync` validates the manifest before preparing ordinary repairs, then persists detached settings without publishing them. It returns the settings dictionary and parsed snapshot; `Initialize` publishes the prepared snapshot after repairs complete, without parsing again. The ten ordinary defaults plus the manifest make eleven first-install configuration rows; no account is seeded. Startup still reloads committed preferences after that transaction before publication, including when verifying a lost commit acknowledgment. Manifest history has no runtime singleton or ordinary settings writer. A nonempty database without a recognized ordinary-group or manifest row fails before repair writes; unknown keys and inert legacy credentials do not establish installation configuration. Account absence or a profile without credentials is a valid Local setup state. A missing manifest with existing ordinary configuration is reconstructed with unknown version and current reconstruction time, with a Warning; valid saved metadata remains unchanged. Do not replace a failed new-install transaction with a permanent manual-recovery requirement: after rollback, an empty schema must remain retryable.
- `Moonglade.Setup.WebApplicationExtensions.InitStartUp` runs before the Web pipeline/endpoints and host start. An initialization failure logs Critical and throws, so the process exits nonzero without starting HTTP or hosted business services. Never call `RunAsync` to serve an error-only page on the application host: that also starts scheduled publication and other workers against uninitialized settings. Administrators correct the reported cause and restart; failure does not permanently disable retry.
- Ordinary runtime settings writes use `UpdateConfigurationCommand.Create(settings)` for one group per command. The command retains the immutable settings value without JSON copying. Inside the singleton `ConfigurationWriteGate`, validate the submitted value, apply it to the latest captured root, serialize it once for persistence, and save the required row before publishing the complete root. Preserve unrelated concurrent group saves. Whole-group saves replace the entire group. Missing rows and failed writes throw instead of returning an ignored success code. Callers prepare replacements with `with` rather than mutating objects from `IBlogConfig`. Account operations instead use scoped Auth storage and database revision concurrency, with no credential publication through Configuration. Keep secret-bearing account models as plain classes so generated diagnostic strings cannot include secrets. Unchanged ordinary persisted values retain their timestamps while still refreshing the runtime snapshot. Startup initialization remains separate.
- Full and partial ordinary writes return `ConfigurationSaveResult` only after the existing save/publication/invalidation path succeeds. It contains the group type, an effective-change flag, and approved `SettingValueChange` scalar projections, never raw settings. `SettingsChangeProjection` compares the actual prior capture to the saved candidate inside the gate; menu and submenu lists use structural value equality. Keep this comparison separate from raw persisted-JSON equality: normalization or ignored legacy fields may change timestamps/cache events without an effective-change audit, and unchanged persisted JSON may still refresh a stale runtime value. Controllers consume this outcome rather than rereading the root or comparing submitted fields. No-op results return the existing HTTP 204 without audit; restricted-only changes retain an update with no displayable values. Password/authenticator events remain separate and never receive this ordinary-settings value projection.
- `Moonglade.Configuration.SettingsAuditFields` owns the ordered 50 approved audit-value field names across the ten ordinary groups, exposed as immutable arrays. Both `SettingsChangeProjection` and the matching `ActivityEvents` definitions consume this policy; `Moonglade.ActivityLog` references Configuration, never the reverse. Canonical event keys and labels remain in ActivityLog, and Web's PATCH editable-field allowlists remain separate. Preserve field names and casing, including `SiteTitle`. The General and Advanced event definitions also allow historical SEO switch keys and the old General Gravatar key so existing records remain readable.
- `ActivityLogDetails` validates stored settings changes and returns ordered, read-only `ActivityLogSettingChangeDetail` values with detached `JsonElement` scalars. `ActivityLogItem.SettingChanges` is JSON-ignored read-model data: `null` means no settings-change envelope; an empty list represents the valid restricted-only `Changes: []` envelope. Keep the existing raw `Details` dictionary and stored JSON for compatibility, but localize the typed changes in Web without reading persisted `Key`, `OldValue`, or `NewValue` members again. List and detail reads share this validation and must both reject malformed stored details; retain scalar types, historical keys, order, and existing localized label keys.
- Administrator controllers call `BlogControllerBase.LogActivityAsync` only after their business operations complete. Controllers, the post-save workflow, and scheduled publication share the Web-owned `ActivityLogDispatcher` audit-only guard with constructor-supplied logging. Controller auditing remains noncancelable, post-save auditing retains the request token, and scheduled activities use `CancellationToken.None` with captured UTC snapshots and no HTTP context. Audit dispatch failures (including cancellation) preserve the existing success result and emit Error with the canonical event key, failure type, and available trace identifier. The in-process `CreateActivityLogCommand` and `PostOperationContext` carry trace metadata in non-positional, JSON-ignored init-only properties; it is never persisted in activity entities or details. The writer retains its catch/detach contract and owns insert/validation/cancellation diagnostics; the Web guard logs only failures that escape dispatch, avoiding duplicate diagnostics. Keep the existing diagnostic fields/templates when no trace is available. Do not log exception objects/messages, free-form operations, target values, request context, details, or credential fields. Do not put validation, settings persistence, cache events, asset/file operations, or authentication actions inside the audit catch. Authenticator reset must still sign out all three local schemes after an audit-only failure; password changes retain their current session behavior. Asset/file/settings writes remain separate operations, not a new transaction.
- Ordinary settings pages submit only the edited fields via `PATCH` on the owning group routes. The SEO tab follows Notification and collects canonical URL prefix, meta keywords, sitemap, robots.txt, IndexNow, JSON-LD BlogPosting, and Dublin Core metadata (including the license URL). The editable fields live in `SEOSettings` and use `/api/settings/seo` and `settings.seo.updated`. IndexNow remains a read-only display of host configuration. The controller explicitly allows fields per group. `PatchConfigurationCommand` applies them to a copy of the latest group inside the same process write gate, then uses the shared whole-group validation, persistence, and publication path. Existing `POST` requests still replace the group. CDN redirect and Custom CSS can each submit their switch and required content together.
- Changed settings publish one `ConfigurationChangedEvent` after persistence and runtime replacement, while still inside the process write lock, without request cancellation. The Web handler invalidates feeds for General/SEO/Feed/Image changes, sitemap for General/SEO changes, and theme CSS for Appearance changes; Advanced changes wake the scheduler. No-op, validation, missing-row, failed-save, and pre-commit cancellation paths do not publish. Keep this boundary shared by internal writers rather than adding controller-only cache removals.
- FOAF and sitemap use the request's settings capture to return HTTP 404 when disabled, before reading cached content or generating XML. Scheduled publishing captures its wake token and one ordinary root per wait iteration, wakes even while disabled, and rechecks cancellation plus a fresh enable snapshot immediately before dispatch. This post-wait decision is a new operation phase, preserving the disable/wake guarantee rather than pinning the switch across a long wait. Do not cancel already dispatched publication when toggling the flag. Notification decisions within an already captured operation use its switches; independent subsequent operations capture new switches. Previously queued mail retains its persisted payload. The email sender display name intentionally captures once when singleton EmailSettings is created and still requires restart.
- `/admin/settings` is the main UI for blog settings. Do not hard-code administrator-configurable blog behavior in the Web layer.
- `ContentSettings.DefaultEditor` owns the [default post editor](../README.md#default-post-editor). Do not restore the removed host configuration key or historical content-type backfill.

### Authentication And Security

- Authentication logic lives in `Moonglade.Auth` and supports local accounts with TOTP or one standards-based OpenID Connect provider.
- Local authentication uses `OwnerAccount` in `BlogDbContext` and the scoped Auth-owned `OwnerAccountStore`, separate from ordinary settings. `IOwnerProfileReader` projects stable ID, public email, and the account avatar preference. Its identity fields supply Atom, FOAF and owner-directed notifications. Email is trimmed and normalized with `ToUpperInvariant`; database indexes enforce normalized-email uniqueness and a singleton slot constrained to 1. A profile has no local credentials. `LocalInitializedUtc` marks committed local initialization independently of the bound TOTP secret, so clearing that secret does not reopen setup. A revision concurrency token protects competing writes; failed writes detach the attempted entity. Store writes reject enclosing transactions so a returned update represents its own commit.
- `/admin/account` edits public email for both providers. Local changes require the current password and invalidate all Local sessions after a real change, retaining stable ID, credentials and TOTP. An exact trimmed no-op keeps its revision and session. OIDC creates/updates a public profile through an authorized session without a local password or claim-email fallback; its session remains valid. Account Settings owns the public name, description, and email. A missing OIDC profile omits Atom email and FOAF mailbox hash, falls back to local avatars and skips owner-directed notifications; commenter replies are independent. Notification handlers capture the recipient once before queueing. The test-email endpoint rejects missing owner email and passes its captured profile to the handler.
- Atom must retain the post's author name even without public email so the formatter can emit a valid entry. Do not remove the whole author or fabricate an address. RSS retains its existing email-based author serialization.
- Public `/auth/setup-account` has no installation token. While Local credentials are absent, `LocalAccountSetupGateMiddleware` redirects matched browser pages to setup and returns no-store HTTP 503 with Retry-After for business/API/feed/protocol requests. Both health endpoints and setup remain reachable. `MapStaticAssets().ShortCircuit()` serves manifest-mapped fingerprinted assets before this gate; physical `UseStaticFiles` alone cannot serve those routes. OIDC bypasses the gate without reading an account. Initial email/hash/salt and any generated TOTP secret stay in a protected, nonsliding ten-minute ticket until proof succeeds. No raw password persists in the ticket. Required proof and revision/expiry checks precede the single credential commit; success signs in and opens the public homepage.
- Local cookies carry stable account ID and revision. `LocalAccountCookieEvents` rejects pre-upgrade or stale tickets; an application cookie also requires a bound authenticator when TOTP is required. Intermediate cookies never grant Administrator. Password updates refresh the current application cookie, retain TOTP and invalidate stale sessions. Account reloads the email revision after a password update and disables email edits until that refresh succeeds. Password dialogs must accept the same password lengths as setup and sign-in. Password-protected authenticator resets sign out the three Local schemes without reopening initial setup; later enrollment keeps its secret only in the protected intermediate ticket until verification. Ordinary sign-in and re-enrollment open the admin dashboard. `Authentication:Totp:Required=false` skips setup and sign-in proof in every environment.
- OIDC admin authorization uses the provider-validated issuer boundary plus an exact allowlist of stable `sub` claims. Do not authorize by email, display name, or preferred username.
- `/auth/identity` is available only to an authenticated OIDC user and returns that user's own `iss`, `sub`, and display name for allowlist bootstrap; it does not grant admin access. It returns 404 when local authentication is configured.
- Local initial setup, password sign-in and TOTP setup/verification are protected by `LocalAccountRateLimitPolicy`; keep the default 10 attempts per 1 minute unless there is a deployment-specific reason to adjust `Authentication:LocalAccountRateLimit`. All initial setup POSTs, including authenticator proof, share one client-IP quota independent of posted fields or setup tickets. Ordinary sign-in and TOTP retain their account/IP partitions. Unlimited requests use a separate partition-key namespace so cached GET or disabled-policy limiters cannot suppress subsequent POST limits.
- Admin Razor Pages are authorized by Razor Pages conventions; API controllers inherit `[Authorize]` from `BlogControllerBase`.
- Controllers use antiforgery validation by default. Use `[IgnoreAntiforgeryToken]` only for deliberate endpoints such as keep-alive or protocol callbacks.

### Images, Themes, Feeds, And Protocols

- Auth's scoped `OwnerAvatarStore` owns uploaded images and the Gravatar preference in `OwnerAvatar`. The singleton can exist before an OIDC public email is configured. Avatar writes update their own row, leave account revision and ordinary configuration alone, and preserve the other avatar field during concurrent writes. Public views apply Gravatar only when an owner profile exists. Local images use the PathBase-aware `/avatar` route with the bundled default as fallback. Uploads invalidate the Account avatar cache and audit after save. Site icon storage remains in `BlogAsset`.

- Image storage is abstracted in `Moonglade.ImageStorage` and has one filesystem implementation. New image behavior should depend on `IBlogImageStorage`, not on `FileSystemImageStorage`, but the interface is an internal application boundary rather than a supported provider extension model.
- `ImageStorage:FileSystemPath` stores public processed images; `ImageStorage:OriginalFileSystemPath` stores private original uploads. The resolved roots must be absolute, distinct, and non-overlapping. Public reads and deletes must never resolve the original root.
- Cloud object storage, network filesystems, mount drivers, sidecars, CSI manifests, Docker volume plugins, credentials, object metadata, and vendor-specific operational behavior remain outside application code and packages. Do not add Azure, S3, or other vendor image-storage providers or optional extensions.
- CDN delivery stays browser-direct and settings-driven. Persisted content and upload responses use `/image/{filename}`; rendered posts/feeds and the image endpoint use `ImageSettings.CDNEndpoint` when redirects are enabled. A CDN origin may expose only the primary root, must preserve filename-to-key mapping and correct media types, and must never expose original images.
- Image uploads are validated by content before storage. SVG upload is supported, but SVG content must pass through the Web-layer sanitizer before primary or original image bytes are saved.
- Themes and custom CSS are handled by `Moonglade.Theme` and `Moonglade.Web.Middleware.StyleSheetEndpoints`.
- RSS, Atom, and OPML generation lives in `Moonglade.Syndication`; OpenSearch, FOAF, manifest, robots, sitemap, and site verification file handlers live under `Moonglade.Web/Handlers`. RSS/Atom query handlers pass their captured settings explicitly to `SyndicationDataSource`, which has no live settings reader.
- Site verification files are managed from `/admin/settings/verification-files`, persisted in the database, and served as virtual root-level files. They are text-only (`.txt`, `.html`, `.htm`, `.xml`, `.json`), limited to 64 KB, and must use a single safe ASCII file name. Do not write these files into container `wwwroot`.
- Preserve the public protocol endpoints listed in the README, including `/rss`, `/atom`, `/opml`, `/opensearch`, `/foaf.xml`, `/webmention`, `/health`, and `/health/ready`. Keep `/health` liveness-only; use `/health/ready` for database readiness.
- Incoming and outgoing Webmention requests must stay restricted to public HTTP/HTTPS URLs through Edi.AspNetCore.Utils public-HTTP safety services. Reject private, loopback, link-local, documentation, reserved, and other special-use source, target, redirect, or endpoint addresses. Keep socket connections bound to validated DNS results and do not enable automatic redirects, cookies, proxies, or ambient credentials on these clients.

## Code Architecture

### Layers And Project Responsibilities

| Area | Path | Responsibility |
| --- | --- | --- |
| Web host | `src/Moonglade.Web` | ASP.NET Core composition root, Razor Pages, API controllers, view components, filters, handlers, endpoint mapping, and static assets. |

### Web Entry Point

- `src/Moonglade.Web/Program.cs` should stay as startup orchestration: load business assemblies, create the builder, register services, build the app, run startup initialization, attach the request pipeline, and map endpoints.
- Reusable service registration belongs in `IServiceCollection` extension methods in the owning project. Compose Web-host services in `src/Moonglade.Web/Extensions/ServiceCollectionExtensions.cs`, and avoid adding feature-specific registration details directly to `Program.cs` unless the Web host is genuinely the owner.
- Request pipeline and endpoint mapping are centralized in `src/Moonglade.Web/Extensions/WebApplicationExtensions.cs`.
- If a new project contains LiteBus handlers, confirm `Program.LoadAssemblies()` loads that assembly; otherwise command/query/event handlers may not be discovered at runtime.

### CQRS And LiteBus

- The repository uses LiteBus 7.0.0 with a command/query/event style.
- Commands mutate state and are usually named `CreateXCommand`, `UpdateXCommand`, or `DeleteXCommand`, with matching `*Handler` classes in the same or nearby files.
- Queries read state and are usually named `GetXQuery`, `ListXQuery`, or `CountXQuery`.
- The Activity Log event-types endpoint reads the immutable `ActivityEvents.All` catalog directly, orders canonical groups and keys with `StringComparer.Ordinal`, then localizes labels. Persisted history list and detail reads remain LiteBus queries; do not sort filter options by localized text.
- Events trigger side effects such as email, Webmention, IndexNow, or background notifications.

### EF Core

- Use `BlogDbContext` for data access. Add entities under `Moonglade.Data.Entities` and DTO/read models under `Moonglade.Data.DTO`.
- Prefer provider-neutral configuration in `Moonglade.Data.Configurations`; SQL Server/PostgreSQL-specific behavior belongs in the provider projects.
- PostgreSQL converts table and column names to snake_case in `PostgreSqlBlogDbContext`; SQL Server retains PascalCase mappings. Keep C# names unchanged. Existing PostgreSQL databases require the [manual naming upgrade](upgrade-postgresql-snake-case.md) after any required category integer ID upgrade. Constraint, index, and sequence names are retained during this upgrade.
- Keep queries compatible with both SQL Server and PostgreSQL. Avoid scattered provider-specific SQL; isolate it in provider projects if it is truly necessary.
- Prefer `AsNoTracking()` for read-only queries. Use async EF Core APIs and pass `CancellationToken` through write operations and handlers where available.
- Use EF Core set-based operations such as `ExecuteDeleteAsync` when they fit the existing pattern.
- Activity history persists canonical `ActivityEvents` keys, required UTC time, explicit `ActivityActorKind`, optional actor/target snapshots, and allowlisted structured details. Event definitions own groups and wording keys; Web localizes filter, summary, and detail headings from those definitions. Never copy protected settings, comment reply bodies, category notes, or verification file contents into activity details. Writes are best effort, and failed inserts detach only the attempted activity entity.
- Ordinary settings events require `{"Changes":[{"Key":"SiteTitle","OldValue":"Previous","NewValue":"Saved"}]}` with approved per-group field names, unique changed keys, exact members, and scalar typed values. Configuration owns projection, while ActivityLog validates the envelope on writes and reads. The metadata API exposes localized `changes` with typed `oldValue`/`newValue` for ordinary settings events and `fields` for other events. An empty changes array identifies a real update without permitted display values. Render all values as text with localized boolean/enum choices. Clear pre-release activity rows at the [release cutover](upgrade-activity-log-events.md#reset-an-already-upgraded-preview).
- Be careful with many-to-many relationships, cascade behavior, slug/route link generation, publish timestamps, and soft-delete fields because posts, lists, archives, tags, feeds, sitemap, and cache invalidation depend on them.
- `Category.Id` and `PostCategory.CategoryId` are `int`; both supported provider contexts configure category identity generation from 100 with increment 1. Category creation and fresh seeding must leave the ID to the database. Administrative category APIs and post-editor DTOs use integers; public category and subscription URLs retain slugs. Existing GUID category databases require the [manual category upgrade](upgrade-category-int-identity.md).
- Persisted `DateTime` properties whose names end in `Utc` use the shared UTC contract: SQL Server `datetime2(7)`, PostgreSQL `timestamp with time zone`, UTC materialization, and rejection of local or unspecified tracked writes. `PostViewDaily.ViewDateUtc` is a `DateOnly` stored as `date`.
- Browser wall-clock values are accepted only by Web request DTOs. Convert them with the supplied IANA time zone before dispatching feature commands; feature models and persisted values must contain UTC timestamps only.
- Follow the [manual migration rules](../database/README.md) for schema/data changes. Preserve fresh creation/seeding; do not restore automatic upgrades or enable `Npgsql.EnableLegacyTimestampBehavior`.
- Independent owner-account upgrades require additive `owner-account.sql` followed by `owner-account-cutover.sql` for the provider, with all hosts stopped and a backup. The cutover transfers only legacy public email into an absent profile, preserves configured accounts on reruns, removes that General member and deletes only the obsolete credentials row. No legacy credentials are imported. See the [upgrade guide](upgrade-owner-account.md). Fresh creation, startup emptiness checks and full-database clearing include the table. PostgreSQL reapplies shared account check constraints after translating column names; keep fresh mappings and manual schema definitions aligned.

## Caching And Side Effects

- Configuration-dependent output cache keys retain their existing post/theme invalidation generations and also include captured input identity: a SHA-256 fingerprint of General/Feed/Image JSON and the captured account description for feeds, plus captured owner email (including absence) for Atom, General JSON for sitemap, and configured theme ID for theme CSS. Atom passes the same captured profile to its query; no ambient profile fallback inside the factory. `OwnerProfileChangedEvent` advances feed generations after a committed profile creation, Local setup or real email change without request cancellation; no-op writes publish nothing. It does not flush articles. Public layout/profile rendering shares a credential-free nullable profile through ViewData. Cached tag HTML varies by captured hot-tag count. Do not substitute an ambient live read inside a cache factory or flush unrelated article partitions; inactive entries expire under their normal cache lifetime.

- Write operations must consider cache impact. Changes to posts, pages, categories, tags, widgets, configuration, themes, comments, and assets can affect page caches, post caches, sitemap, feeds, archives, tag/category lists, and widget caches.
- Existing caching uses `Edi.CacheAside.InMemory` and `BlogCachePartition`. Successful post content, metadata, and lifecycle writes, plus category/tag updates and deletes, publish `PostChangedEvent` once after database commit. The Web event handler uses the singleton `PostCacheInvalidator` to clear the entire `Post`, `RssCategory`, and `AtomCategory` partitions and advance post/feed/sitemap generations. Old RSS, Atom, and sitemap entries in `General` expire normally. Publish without request cancellation so a disconnected client cannot skip invalidation after a successful commit. Failed writes, missing objects, empty batches, and view/request count updates do not invalidate these caches.
- Post readers use `PostCacheInvalidator.GetCacheKey`, feed readers use `GetFeedCacheKey(key, settings)`, and sitemap readers use `GetSiteMapCacheKey(settings)`. Separate versions prevent older in-flight queries from repopulating active caches and let settings refresh feeds or sitemap without flushing article caches. Successful post changes still invalidate all three. Sitemap and feeds expire after one hour. Other controller caches retain their existing rules and `ClearBlogCache` filter. All invalidation is local to the current process.
- Public/admin/auth layouts share `ThemeCacheInvalidator.GetCacheKey(themeId)`; appearance saves and successful theme create/delete operations advance its generation. Old theme entries expire normally. Theme conflict/not-found/failure paths do not invalidate. Preserve unknown-theme fallback. Custom CSS continues to use its HTTP ETag/cache policy; server generations cannot purge downstream caches. Full-feed content comes from `PostContent`, formatted by content type and CDN settings; summary mode uses `ContentAbstract`.
- Prefer centralized invalidation through filters or event handlers over scattered controller-level `cache.Remove(...)` calls when adding new write paths.
- For post and page writes, review sitemap, feed/subscription, per-post/page, archive, tag/category, and widget cache impact.
- For settings and theme changes, review site-wide rendering, custom CSS, manifest, robots, FOAF, and sitemap impact.
- Publishing posts can trigger Webmention and IndexNow. Comments, replies, and Webmentions can trigger email notifications. New side effects should usually be events or background work through existing services such as `CannonService`, LiteBus events, `IWebmentionSender`, `IIndexNowClient`, and the email outbox instead of slow inline request work.
- `CannonService` is an in-process bounded queue controlled by `CannonService:QueueCapacity`; do not run overflow work inline on request paths.
- Preserve hosted service patterns for scheduled publishing. Configuration-driven background behavior should remain controlled by `appsettings` values.

## Migration Verification

No automatic migration implementation, embedded migration SQL, or migration version-check tests remain. Startup tests cover existing databases with missing or older installation manifests and preserve stored content and manifest values. Startup does not check database version compatibility; administrators must complete required SQL upgrades before launching the new version.

Run `Moonglade.Setup.Tests` when changing database mappings, initialization, or upgrade documentation. Follow [database verification and execution](../database/README.md#verification-and-execution), including representative pre-upgrade and repeat runs on both target providers. Review UTC conversion, transactions, dependent keys/indexes, and backup rollback. In-memory tests and source review do not prove relational correctness or idempotency; report unavailable database verification explicitly.

Category identity and snake_case migration tests use opt-in disposable PostgreSQL and SQL Server containers. See the [category upgrade guide](upgrade-category-int-identity.md#automated-verification) for the Docker prerequisites and `MOONGLADE_TEST_CATEGORY_DATABASES` command; a normal test run skips these relational groups explicitly.

The [SEO settings upgrade](upgrade-seo-settings.md) copies existing SEO values into their own configuration row before startup. The robots.txt follow-up copies the legacy content from Advanced after that row exists. The scripts preserve the legacy rows and current SEO values on reruns.

The filesystem-only image-storage cutover is documented in [upgrade-filesystem-image-storage.md](upgrade-filesystem-image-storage.md).

The [canonical activity event upgrade](upgrade-activity-log-events.md) requires a stopped host and the standard legacy activity schema after prior naming/category upgrades. Manual scripts discard only legacy activity rows during the schema transition; a complete upgraded schema is a no-op preserving new history. Fresh installations use the normal EF schema creation. Activity API clients use repeated `eventKeys` strings and structured metadata, not numeric event filters or persisted free-form operation text.

## Change Impact Checklist

1. Which business module owns this change? Prefer the owning class library over putting business rules in `Moonglade.Web`.
2. Does it affect database queries, entities, configuration, or database-provider behavior? Check SQL Server and PostgreSQL compatibility.
3. Does it change post URLs, publish timestamps, status transitions, caches, feeds, sitemap, Webmention, IndexNow, or email notifications?
4. Does it require updating `Program.LoadAssemblies()`, a DI extension, default configuration, resource files, or tests?
5. Does it add an external call? Make it configurable, testable, logged, and avoid blocking the main request.
6. Does it touch a security boundary? Check authentication, authorization, antiforgery, moderation, secret configuration, and forwarded headers.
7. Does it affect image storage or CDN behavior? Check primary/original path isolation, filename-to-key mapping, direct browser delivery, mount persistence and permissions, multiple replicas, and the filesystem-only vendor boundary.
8. Does documentation need to change? The README, root AGENTS.md, and this reference should reflect important developer-facing behavior.
